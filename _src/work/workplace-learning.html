AI-Assisted Course Authoring as Workplace Learning

A design-based research program on the Course Building Assistant, a multi-agent course-design system used by course teams developing online learning solutions for various audiences, including Harvard Online. The program approaches the system's use as workplace learning, in which the instructional designers, technologists, and faculty who use it develop new professional practice and that practice informs the design.

Context

AI authoring tools are usually evaluated on productivity, but when course teams are learning to design with AI, the tool also determines which parts of the craft they continue to practice and which they hand off, so its design carries consequences for workplace learning as well as output. The guiding question was therefore twofold: which parts of course design the system should perform, and which should remain with the people whose expertise it is meant to extend.

The system

The Course Building Assistant, which I designed and built with Claude Code, coordinates specialized agents through three human approval gates. It supports eight pedagogical styles, a taxonomy of 20 teaching-element types, and course outlines whose units are linked to prerequisites and course outcomes. Four evaluators review each draft for persona-based quality, pedagogical fidelity, narrative coherence, and copyediting, each informed by deterministic pre-scans. The system moved from concept to institutional use in about six months, across eight releases between June and September 2026 and with 437 automated tests.

It is in use across a growing set of Harvard Online course builds, and its manuscript-to-build-document pipeline is in pilot with instructional technologists. A build guide, an in-app manual, and an MIT-licensed, self-hosted distribution allow other teams to run and adapt the system independently.

Method

The work follows design-based research, in which each release functions as a conjecture tested in practice and revised in light of what practitioners do.1 Qualitative data include interviews and conversations with course team members, analytic memos, and field notes from build sessions, analyzed through a grounded theory approach that allows categories to emerge from the data.2 Cultural-Historical Activity Theory then frames the tensions among those categories within an activity system of people, tools, rules, and divisions of labor.3 Quantitative traces include time to build and usage logs recording how each generated element was kept, revised, or regenerated. I verify these traces against the qualitative record before drawing conclusions from them, consistent with established criteria for trustworthiness in naturalistic inquiry.4

Findings

Three findings from this fieldwork redirected the design of the system.

Augmenting faculty expertise

Reviews of early modules showed that, when given a faculty member's existing prose, the system tended to rewrite it rather than build on it. In discussion with production colleagues, the team adopted the principle that AI should augment faculty work, and I codified that principle in the governing build guide. Four recurring defects are now tracked by count rather than impression: replacing faculty voice instead of extending it, fragmenting interview transcripts, fabricating citations or frameworks, and introducing framework labels where the design calls for inductive learning. A current pilot compares two model configurations for one agent role using blind scoring against those counts, with the decision rule specified before results are available.

Designing around authorship

Fieldwork showed that many course teams begin with a manuscript they have already written, and that early versions of the system could overwrite their revisions. Manuscript import is now the primary workflow in the system: five deterministic parsers bring a written course into the platform's structure without an AI call, edits survive a round trip exactly, and human-authored manuscripts are exempt from automated AI review by default. Over several months the system moved from an author that staff supervised to an assistant organized around their authorship, and each of these changes was at once a product decision and a learning design decision, because each altered what course teams practice themselves.

Locating human judgment

Instructional technologists described building pages by hand as the point at which they ask whether each element is the right teaching choice, which positions the build as a site of reflection-in-action as well as production.5 Wholesale automation would save time while, I expect, removing a source of course quality. The design response was to automate verification rather than construction, producing a punch list of remaining issues for a finished build, and to make build automation optional. A generated build document reduces the technologist's step to an estimated 30-minute review, and because adoption is optional, efficiency gains are best reported as an adoption curve rather than a single figure. The optional design also creates a natural comparison between teams who automate and teams who build by hand.

Extending the approach

The same attention to how designers work informs a multivocal framework now in development for courses whose faculty, drawn from different disciplines, were never recorded together. The framework indicates where each discipline's perspective belongs in the narrative so that a course can carry several faculty voices through a single coherent argument.

A related design principle, separating what the model should judge from what code should guarantee, is discussed in Model Judgment and Deterministic Verification in AI-Assisted Course Authoring.
